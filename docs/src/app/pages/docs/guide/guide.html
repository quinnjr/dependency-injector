Guide

Deep dive into dependency-injector's features and advanced usage patterns.

Scoped Containers

Scoped containers allow you to create hierarchical dependency trees. Child scopes inherit all services from their parent but can also register their own services or override parent services.

Common Use Cases

  • Request-scoped services - Create a scope per HTTP request with request-specific context
  • Testing - Override production services with mocks in test scopes
  • Multi-tenancy - Create tenant-specific scopes with tenant configuration

Service Overrides

Child scopes can override services from parent scopes. This is particularly useful for testing, where you want to replace real implementations with mocks.

Compile-Time Safety

Beyond the dynamic Container, dependency-injector ships two compile-time layers: the typed builder, which records registrations in the type system, and verified services, which declare their dependencies through a trait so the container can resolve and wire them for you.

TypedBuilder & TypedContainer

TypedBuilder tracks every registration in its type parameter. Calling build() locks the container against further registrations and returns a TypedContainer whose get() returns Arc<T> directly — no Result handling for services you registered. try_get() and contains() remain available for defensive code paths, and scope() still hands out dynamic child containers.

Verified Services

Implement the Service trait to declare a service's dependencies and construction logic. Dependencies can be any Resolvable type: () for none, Arc<T> for one, Option<Arc<T>> for an optional service, or tuples of up to 12 elements that freely mix required and optional entries. The ServiceProvider extension trait on Container then registers services with provide() (lazy singleton), provide_singleton() (eager — returns false when a required dependency is missing), or provide_transient() (new instance per resolve).

Service Modules

Group related registrations behind a ServiceModule so an entire subsystem can be installed with a single call.

Require & TypedRequire

The Require trait declares a service's dependencies as a type-level Reg list that mirrors the typed builder's registry type, so a missing or misordered registration becomes a compile error instead of a runtime panic. With the derive feature enabled, #[derive(TypedRequire)] generates the impl from #[dep] field attributes; #[dep(optional)] fields are excluded from the required list.

Thread Safety

Dependency Injector is designed to be fully thread-safe. All containers can be safely shared across threads using Arc. The internal storage uses DashMap for lock-free concurrent access.

Performance Tip

For hot paths where you resolve the same service frequently, consider caching the Arc<T> reference instead of calling get() repeatedly.

Performance Tools

  • ScopePool - Pre-allocates reusable request scopes; acquire() hands out a scope that is cleared and returned to the pool when dropped (~20ns per reuse vs ~134ns for a fresh scope)
  • warm_cache::<T>() / clear_cache() - Pre-populate or release the thread-local hot cache for services resolved on the hot path
  • lock() / freeze() - lock() forbids registrations after startup; with the perfect-hash feature, freeze() additionally snapshots the container into a FrozenStorage backed by a minimal perfect hash function for collision-free O(1) lookups

Error Handling

Service resolution returns a Result type. The main error cases are:

  • DiError::NotFound - Service type not registered in container or parent scopes
  • DiError::CircularDependency - Circular dependency detected during resolution
  • DiError::CreationFailed - Factory reported a failure while creating the service

Note that factory panics are not caught by the container — a panicking factory propagates the panic to the caller rather than returning an error.
